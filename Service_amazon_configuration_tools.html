1. Configuration Details

Путь: CALLING THE SP-API > Configuration Details

Configuration for calls to the SP-API. This section covers details that help you format calls to the Selling Partner API (SP-API). To make valid SP-API requests, you need to:

  • Direct your calls to the correct regional endpoint.
  • Specify the appropriate marketplace for your request.
  • Format the date and time data correctly.
  • Know which operations require seller authorization.

1.3 Date and Time Formatting

Путь: CALLING THE SP-API > Configuration Details > Date and Time Formatting

Format dates and times for the SP-API. The Selling Partner API (SP-API) formats dates and times similarly to the RFC 3339 standard, which defines a subset profile of ISO 8601 for use in internet protocols and standards.

DateTime

Date and time data is expressed as Gregorian calendar dates (year, month, day) and 24-hour time. No truncated formats are allowed. All date and time data is expressed numerically with leading zeros preserved.

DateTime string patterns are:

  • yyyy-MM-ddTHH:mm:ss.sssZ (for UTC)
  • yyyy-MM-ddTHH:mm:ss.sss±hh:mm (for a local time offset)

The character T is a required delimiter between the date and time sections. The colon (:) is used as a delimiter between hours, minutes, and seconds. Fractional seconds are expressed with a decimal mark (. or ,) when needed.

All use of date and time data in SP-API should be expressed as type DateTime. However, there are a few parameters that express date or time as a simple string. Check the parameter type definition to be sure of which type to use. Using the wrong type will generate an error.

Example:

2016-03-16T14:32:16.50-07

This example is read as the 16th day of March in 2016 at 14 hours, 32 minutes, and 16.50 seconds local time. The local time is seven hours behind UTC.

1.4 Grantless Operations

Путь: CALLING THE SP-API > Configuration Details > Grantless Operations

A grantless operation is an operation that you can call without explicit authorization from a selling partner. This means that when you request a Login with Amazon access token prior to calling a grantless operation, you don't need to provide a refresh token. Instead, you use the scope parameter to provide the scope of the LWA authorization grant.

For example, if you use a generated Java SDK to call grantless operations, use the withScopes parameter to set one or more scopes for the LWA authorization grant when you configure your LWA credentials.

2. Call Structure

Путь: CALLING THE SP-API > Call Structure

Learn how to send requests and handle responses. When you call the Selling Partner API (SP-API), you must:

  • Structure your request correctly, including all required parameters and headers.
  • Send the request to the appropriate endpoint.
  • Process the response headers and messages, and take appropriate action.

2.1 Connect to the SP-API

Путь: CALLING THE SP-API > Call Structure > Connect to the SP-API

How to connect to the SP-API. Before your application can connect to SP-API, you must:

  • Register the application.
  • Get the application authorized by a selling partner or, if you're a private developer, authorize it yourself.

An Login with Amazon (LWA) access token authorizes your application to take certain actions on behalf of a selling partner. An LWA access token expires one hour after it is issued.

Note: An LWA access token must be included in calls to all operations except restricted operations, which return Personally Identifiable Information (PII). When calling restricted operations, replace the LWA access token with a Restricted Data Token (RDT).

Request an LWA Access Token

To request an LWA access token, make a secure HTTP POST to the LWA authentication server (https://api.amazon.com/auth/o2/token) with the following parameters:

NameDescriptionRequired
grant_typeThe type of access grant requested. Use refresh_token for authorized operations or client_credentials for grantless operations.Yes
refresh_tokenRequired for authorized operations.No
scopeRequired for grantless operations (e.g., sellingpartnerapi::notifications).No
client_idProvided during application registration.Yes
client_secretProvided during application registration.Yes

Example for operations requiring selling partner authorization:

POST /auth/o2/token HTTP/1.1
Host: api.amazon.com
Content-Type: application/x-www-form-urlencoded;charset=UTF-8
grant_type=refresh_token
&refresh_token=Aztr|...
&client_id=foodev
&client_secret=Y76SDl2F

Example for grantless operations:

POST /auth/o2/token HTTP/1.1
Host: api.amazon.com
Content-Type: application/x-www-form-urlencoded;charset=UTF-8
grant_type=client_credentials
&scope=sellingpartnerapi::notifications
&client_id=foodev
&client_secret=Y76SDl2F

3. Development Tools

Путь: CALLING THE SP-API > Development Tools

Tools and environments for testing SP-API calls. Before you deploy your SP-API integration to production, you can test and validate your implementation by using dedicated testing tools and environments.

3.1 Selling Partner API Sandbox

Путь: CALLING THE SP-API > Development Tools > Selling Partner API Sandbox

Use the SP-API sandbox to make test calls. The SP-API provides two sandbox environments to test your applications without affecting production data:

  • Static sandbox: Returns pattern-matching mock responses for all SP-APIs.
  • Dynamic sandbox: Routes requests to a sandbox backend that returns realistic, stateful responses.
Important Notes:
  • Throttling limits: 5 requests per second (rate), 15 burst.
  • Restricted Data Token (RDT): If a sandbox call requires RDT, it must be obtained from the production environment and passed to the sandbox.

Static Sandbox

Procedure for Static Sandbox Call:

  1. Locate the API's Swagger model JSON file.
  2. Identify the x-amzn-api-sandbox object with "static" arrays.
  3. Use the example parameters from the JSON to construct your request.
  4. Direct your call to the sandbox endpoint (e.g., sandbox.sellingpartnerapi-na.amazon.com).

Dynamic Sandbox

Support Requirement: Must include the x-amzn-api-sandbox: {"dynamic": {}} object in the Swagger model (at the operation or path level).

Procedure: Direct valid API requests to the sandbox endpoint, as in production calling.

Sandbox-Only Operations

Definition: Operations with "x-amzn-api-sandbox-only": true in the Swagger model.

Purpose: Enable test workflows not possible in production (e.g., creating data items only available via UI).

3.2 Using Postman for Selling Partner API Models

Путь: CALLING THE SP-API > Development Tools > Using Postman for Selling Partner API Models

This document explains how to set up and use Postman for Selling Partner API (SP-API) models. You can use Postman to generate Login with Amazon (LWA) access tokens, import SP-API models, make calls to SP-API endpoints, and make calls to SP-API sandbox endpoints.

Tip: The Amazon Selling Partner API Postman workspace provides ready-to-use collections and flows for multiple use cases and workflows.
  • Getting Started with SP-API for Sellers
  • Getting Started with SP-API for Vendors

Prerequisites

  • LWA client_id and client_secret: Obtained after registering your application.
  • LWA refresh token: Generated after authorizing your application.
  • SP-API endpoint: Refer to SP-API Endpoints documentation.

Generate an LWA Access Token

  1. Open Postman and sign in to your account.
  2. Select your workspace and create a new HTTP Request (POST method).
  3. Use the URL: https://api.amazon.com/auth/o2/token
  4. Set the Body to x-www-form-urlencoded with these parameters:
KeyValue
grant_typerefresh_token
refresh_token[your refresh token]
client_id[your client ID]
client_secret[your client secret]

Response:

{
  "access_token": "Atza|*****",
  "refresh_token": "Atzr|*****",
  "token_type": "bearer",
  "expires_in": 3600
}

Import an SP-API Model

  1. Navigate to the selling-partner-api-models GitHub folder.
  2. Download the desired API model JSON file.
  3. In Postman, Import the JSON file as a Postman Collection.

Call an SP-API Endpoint

  1. Select your Postman workspace and open the imported collection.
  2. Choose a GET operation.
  3. Add the authorization header: x-amz-access-token: [your access token]
  4. Send the request.

Call an SP-API Sandbox Endpoint

  1. Follow import steps above using the SP-API Sandbox endpoint URL.
  2. Set {{baseUrl}} to the SP-API Sandbox.
  3. Include required parameters from the model.
  4. Add the authorization header: x-amzn-access-token: [your access token]
  5. Send the request and validate the response matches the model.
