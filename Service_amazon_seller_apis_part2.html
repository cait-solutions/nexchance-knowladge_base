1. FBA Inbound API (Fulfillment Inbound)

Путь: SELLER APIs → FULFILLMENT INBOUND API
URL: https://developer-docs.amazon.com/sp-api/docs/fulfillment-inbound-api

1.1 Обзор API

Fulfillment Inbound API используется для создания и обновления входящих запасов в сеть выполнения заказов Amazon, где Amazon может выполнять заказы ваших клиентов. Вы также можете запрашивать списки входящих отправок или товаров на основе указанных критериев.

ПараметрЗначение
Текущая версияv2024-03-20
Legacy версииv0
ДоступностьSellers only
SandboxStatic
❗ Важно: Начиная с 1 января 2026, услуги подготовки и маркировки товаров больше не будут доступны для FBA на рынке США. Продавцы должны подготовить и промаркировать товары перед отправкой в центры выполнения Amazon в США.

Ключевые возможности Fulfillment Inbound API:

  1. Создание входящей отправки: Используйте POST операции для определения новых планов и вариантов доставки.
  2. Получение деталей отправки: Используйте GET операции для доступа к информации об отправке.
  3. Обновление планов: Используйте POST для изменения атрибутов, таких как названия или tracking ID.
  4. Удаление планов: Используйте PUT для удаления существующих планов.
  5. Интероперабельность: Планы, созданные через API, могут быть доступны/редактированы в UI Amazon (Send to Amazon) после подтверждения размещения и транспортных опций.
💡 Совет: Используйте generatePlacementOptions и generateTransportationOptions для создания новых опций. Переключение на STA (Send to Amazon) до подтверждения отменит ранее сгенерированные API опции.

Примеры использования:

  1. Создание отправки с известной информацией о коробках
  2. Создание отправки без известной информации о коробках (только LTL)
  3. Создание отправки с партнерским перевозчиком Amazon (PCP) для SPD/LTL/FTL
  4. Создание отправки с не-партнерским перевозчиком для SPD/LTL/FTL
  5. Отправка запасов в центры выполнения Amazon в Индии
⚠️ Ограничение для Бразилии: Нельзя использовать API для создания отправок в Бразилии.

Не устаревшие операции Legacy v0:

  • getLabels
  • getBillOfLading
  • getPrepInstructions
  • getShipments
  • getShipmentItemsByShipmentId
  • getShipmentItems

Эти операции необходимы для задач создания отправки, таких как печать этикеток коробок и накладных.

1.3 Дополнительная функциональность

Получение списка существующих планов

Используйте операцию listInboundPlans для получения информации о планах на основе критериев продавца. Опции фильтрации включают состояние (например, ACTIVE, SHIPPED, VOIDED), дату создания/обновления и параметры пагинации.

Важно: listInboundPlans использует пагинацию. Последующие вызовы должны использовать те же фильтры, что и исходный запрос.

Получение списка товаров в плане

Используйте listInboundPlanItems для получения деталей товаров для конкретного плана. Фильтруйте по ShipmentID или PackingGroupId. Ответ включает: MSKU, ASIN, FNSKU, владельца этикетки, количество, срок годности, код производственной партии, инструкции по подготовке, группу упаковки.

Получение списка паллет

Используйте listInboundPlanPallets для получения деталей паллет (вес, размеры, возможность штабелирования, ID упаковки), отфильтрованных по ShipmentID или PackingGroupId.

Отмена плана

Отмените план и связанные отправки через cancelInboundPlan. Окно отмены:

  • 24 часа для Small Parcel отправок
  • 1 час для LTL/FTL отправок

Обновление информации в отправке

Шаг 1: Обновление содержимого отправки

Вызовите generateShipmentContentUpdatePreviews с измененными данными коробок/товаров.

Шаг 2: Просмотр изменений и расценок

Используйте listShipmentContentUpdatePreview для оценки предложенных изменений и обновленных транспортных расценок.

Шаг 3: Подтверждение обновлений

Вызовите confirmShipmentContentUpdatePreview с inboundPlanID, shipmentID, contentUpdatePreviewId.

1.4 Миграция с v0 на v2024-03-20

Создание планов входящих отправок

Операция v0 createInboundShipmentPlan заменена несколькими операциями в v2024-03-20:

  • createInboundPlan - создает план
  • generatePackingOptions, listPackingOptions, listPackingGroupItems, confirmPackingOption - определяют какие SKU можно упаковать вместе
  • setPackingInformation - предоставляет детали содержимого коробок
  • generatePlacementOptions, listPlacementOptions, getShipment - просмотр разделения отправок и центров выполнения

Ключевые отличия:

  • destinationMarketplaces заменен на shipToCountryCode и ShipToCountrySubdivisionCode
  • PrepDetailList больше не является входным параметром; категории подготовки должны быть установлены в Seller Central для каждого SKU
  • Сборы и скидки получаются через ответы listPackingOptions и listPlacementOptions

Транспортные опции и стоимость

Операции v0Операции v2024-03-20
putTransportDetailsgenerateTransportationOptions
estimateTransportgenerateDeliveryWindowOptions
getTransportDetailslistTransportationOptions, listDeliveryWindowOptions

Подтверждение транспортных запросов

  • Используйте confirmDeliveryWindowOptions и confirmTransportationOptions
  • Окна доставки должны быть подтверждены для опций с программой DELIVERY_WINDOW_REQUIRED
  • Статус транспорта отслеживается автоматически; не нужно отмечать отправки как "shipped"

Отмена транспортных запросов

  • Используйте cancelInboundPlan вместо voidTransport
  • Сборы отменяются при вызове в пределах окна отмены (24 часа для small parcels, 1 час для LTL/FTL)

2.2 Dynamic Sandbox Guide

Динамическая песочница SP-API позволяет тестировать приложения без влияния на производственные данные или инициирования реальных событий.

Операции с динамическими ответами:

  • cancelFulfillmentOrder
  • createFulfillmentOrder
  • getFulfillmentOrder
  • getFulfillmentPreview
  • getPackageTrackingDetails
  • listAllFulfillmentOrders
  • updateFulfillmentOrder
  • deliveryOffers

Операции со статическими ответами:

  • createFulfillmentReturn
  • getFeatureInventory
  • getFeatures
  • getFeatureSKU
  • listReturnReasonCodes

Тестовые сценарии

Последовательность изменений fulfillmentOrderStatus:

  • Заказ полностью или частично выполнен: Received → Planning → Processing → Complete или CompletePartialled
  • Заказ невыполним: Received → Planning → Unfulfillable
  • Заказ отменен: Received → Planning → Cancelled
📘 Примечание: Операция submitFulfillmentOrderStatusUpdate предназначена только для тестирования. При использовании в production вы получите HTTP 403 ошибку.

FAQ

  • Нужны ли новые credentials для sandbox? Нет, используйте существующие production credentials.
  • Можно ли использовать sandbox для нагрузочного тестирования? Нет, сервис предназначен для интеграционного тестирования.
  • Можно ли просматривать sandbox заказы в Seller Central? Нет, sandbox заказы - тестовые и не видны в Seller Central.
  • Поддерживает ли sandbox уведомления? Нет, уведомления не отправляются для sandbox заказов.

12.1 Обзор

Data Kiosk API используется для отправки GraphQL запросов для получения данных из различных схем, помогающих продавцам управлять бизнесом.

Data Kiosk в настоящее время содержит Seller Sales and Traffic Data. Data Kiosk доступен глобально во всех регионах SP-API: NA, EU и FE.

Ключевые особенности

  • Детальная интерактивная документация: Все схемы данных публично доступны с интерактивным Schema Explorer
  • Domain-based datasets: Использует GraphQL для динамической фильтрации и расширенных запросов
  • Обновления схем: Schema-first подход с непрерывными обновлениями
  • Формат отчетов: Вывод в формате JSONL для упрощенного парсинга
  • Пагинация: Поддержка nextToken для получения больших наборов результатов
  • Безопасность: Видимость запросов ограничена запрашивающим приложением

Data Kiosk vs Reports API

  • Документация: Data Kiosk предоставляет интерактивные конструкторы запросов
  • Функциональность: Data Kiosk позволяет динамическую эволюцию схем и расширенную фильтрацию
  • Deprecation: Reports API будет устаревшим после миграции на Data Kiosk

Обработка запросов

  • Ответы включают data documents (JSONL) для статуса DONE или error documents (JSON) для статуса FATAL
  • Статус DONE без dataDocumentId означает отсутствие данных для параметров запроса
  • Планирование или очередь запросов не поддерживается
  • Применяются лимиты на одновременные запросы для пары продавец/приложение

12.3 Планирование запросов

Основной процесс

  1. Подписка на уведомления: Подпишите SQS очередь на DATA_KIOSK_QUERY_PROCESSING_FINISHED для получения уведомлений о завершении обработки данных
  2. Создание запросов: Отправляйте GraphQL запросы с помощью операции createQuery
  3. Получение данных: Используйте dataDocumentId или errorDocumentId (из payload уведомления) с getDocument для доступа к результатам
  4. Хранение данных: Скачайте и сохраните JSONL файл из documentUrl для анализа

Механизм планирования

Определение параметров

  • Start date: Установите на настоящее или будущее, чтобы избежать backfilling. Для исторических данных используйте ежедневные запросы
  • Frequency: Согласуйте с частотой обновления данных (ежедневно, еженедельно, ежемесячно). Избегайте избыточных запросов

Автоматизация

Используйте AWS EventBridge для планирования повторяющихся задач через cron/rate выражения:

  • Автоматический сдвиг дат
  • Выполнение createQuery по расписанию
  • Непрерывный сбор данных

Обработка ошибок и лучшие практики

  • Избегайте избыточности: Проверяйте уникальность запросов для предотвращения дублирования данных
  • Логирование ошибок: Фиксируйте ошибки при отправке запросов/получении данных. Используйте errorDocumentId для изоляции проблем
  • Retry logic: Реализуйте exponential backoff для throttled запросов
  • Мониторинг: Настройте real-time алерты для сбоев запросов, превышения rate limits, чрезмерных задержек обработки

13. Application Management API

Путь: SELLER APIs → Application Management API
Версия: v2023-11-30
Доступность: Sellers and Vendors
Sandbox: Static

13.1 Обзор

Application Management API используется для программной ротации client secret на зарегистрированных приложениях.

Use Cases

  • Set up credential rotation notifications: Настройка уведомлений о ротации учетных данных в Amazon SQS очереди
  • Rotate your application's client secret: Вызов операции rotateApplicationClientSecret для ротации client secrets

Ключевые требования рабочего процесса

Необходимо зарегистрировать Amazon SQS очередь для получения учетных данных перед вызовом API:

  • Новый client secret создается при вызове API и отправляется в SQS очередь с временем истечения старых учетных данных
  • Обновите приложение для использования новых учетных данных до истечения срока действия старых

Лучшие практики

  1. Используйте уведомления об истечении для инициации ротации на основе предоставленного времени истечения
  2. Включите server-side encryption для SQS и предоставьте Amazon доступ на запись в очередь
  3. Храните учетные данные в vault (например, KMS custom keys) и избегайте незашифрованной передачи
  4. Тестируйте интеграцию на draft приложении перед production deployment
