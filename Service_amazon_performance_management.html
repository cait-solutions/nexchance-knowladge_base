2. Usage Plans and Rate Limits

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits

Learn about usage plans and how rate limits are used in SP-API.

API reliability depends on sizing your capacity and resources to meet the changing needs of your application over time. For this reason, the Selling Partner API (SP-API) defines usage plans to control the number of requests that you can make to an operation within a certain time period.

Usage plans depend on several factors. These factors can include the selling partner account, the application that calls the SP-API on behalf of the selling partner account, the marketplace, and so on.

2.1 Rate-Limiting Algorithm

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits > Rate-Limiting Algorithm

The SP-API uses the token bucket algorithm to rate-limit requests to the API. The algorithm is based on the analogy of a bucket containing tokens, where each token can be exchanged for an API request.

  • The SP-API adds tokens to your bucket at a set rate per second until the maximum limit (burst rate) is reached.
  • Each request subtracts a token from the bucket. Throttling occurs when the bucket is empty, resulting in a 429 error.

Example Illustration:

  1. The bucket (burst limit of 2) is full. A request at 01:00:100 depletes one token (1 remains).
  2. A second request at 01:00:200 uses the last token. The bucket is now empty.
  3. A third request at 01:00:300 is throttled because the bucket is empty.
  4. After 1 second (01:01:000), one token is added (rate of 1 token/second).
  5. One more token is added at 01:02:000 (bucket now has 2 tokens).
  6. At 01:03:000, no token is added because the burst limit is reached.
Note: Token buckets may vary for different selling partner/application pairs, regions, or applications.

2.2 Determining Usage Plans

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits > Determining Usage Plans

Rate and burst limits depend on:

  1. API Operation: Each operation has predefined limits (see API references).
  2. Selling Partner and Application Pair: Limits are account-specific (grantless operations are exceptions).
  3. Regions and Marketplaces: Limits are tied to marketplace-specific accounts.

2.3 Usage Plan Types

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits > Usage Plan Types

  1. Standard Usage Plans: Static limits based on expected call patterns (e.g., A+ Content API Rate Limits).
  2. Dynamic Usage Plans: Automatically adjusted based on business metrics. Rates may change without increasing from frequent requests.

2.4 How to Find Your Usage Plan

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits > How to Find Your Usage Plan

  1. SP-API Rate Limit Pages: Check each API's rate limit documentation.
  2. Response Header: Use the x-amzn-RateLimit-Limit header (20x/400/404 responses only).

2.5 Frequently Asked Questions

Путь: CALLING THE SP-API > Performance Management > Usage Plans and Rate Limits > FAQ

The rate limits for one operation are too low for my use case. Can the limit be increased?

Optimize call patterns (batch requests, reduce polling, use push notifications). Dynamic limits may auto-adjust based on business metrics.

How should my application handle a 429 response?

Use a back-off strategy. Retry with exponential delay. Check the x-amzn-RateLimit-Limit header for plan details.

How can I test my application with respect to its usage plans?

Use the SP-API sandbox (note: sandbox limits are shared). Test 429 handling.

Can my application completely avoid getting throttled?

Account for transient throttling (429s). Avoid hardcoded timers. Use event-driven patterns.

What should I do if my application is consistently throttled?

  • Reduce call frequency within limits.
  • Use batch APIs (e.g., Feeds/Reports APIs).
  • Optimize by aligning with assigned rate limits.

Will my application be throttled more often as I obtain more authorizations?

No. Usage plans are account/application pair-specific.

Will rate limits change?

Changes are communicated in advance. Dynamic limits auto-adjust; static limits remain consistent unless updated.

What is the overall goal of dynamic usage plans?

Ensure limits are right-sized to business context, avoiding over/under-sizing.

What factors influence dynamic usage plans?

Selling partner business metrics (not historical request counts).

How often will the limits change?

Limits update when meaningful business metric changes are detected.

3. Optimize Calls to the Selling Partner API

Путь: CALLING THE SP-API > Performance Management > Optimize Calls to the Selling Partner API

Build efficient Selling Partner API integrations through optimized request patterns. This guide outlines strategies to optimize your retrieval (GET API) call patterns and build efficient, cost-effective integrations.

3.1 Batch Operations

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Batch Operations

The SP-API supports batch operations, allowing up to 20 requests in a single API call. Supported operations include:

  • Catalog API: searchCatalogItems
  • Offer/Pricing Info: getCompetitiveSummary, getFeaturedOfferExpectedPriceBatch, getItemOffersBatch, getListingOffersBatch
  • Fee Estimates: getMyFeesEstimates

3.2 Bulk Data Download

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Bulk Data Download

For large datasets:

  • Use Reports API for inventory, order fulfillment, FBA reports, tax, and performance data.
  • Use Data Kiosk API (GraphQL-based) for dynamic, custom queries to access bulk datasets.

3.3 Event-Driven Architecture

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Event-Driven Architecture

Utilize the Notifications API to receive real-time updates instead of polling. Benefits:

  • Automatically trigger actions on events (e.g., listing status changes, order updates).
  • Supports Amazon SQS or Amazon EventBridge workflows.

3.4 Reduce Errors

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Reduce Errors

Monitor HTTP status codes and resolve issues:

Status CodeDescription
400 Bad RequestInvalid or incomplete request (e.g., missing parameters).
403 ForbiddenAuthentication/authorization failure (e.g., invalid access token).
404 Not FoundNon-existent resource.
429 Too Many RequestsExceeded rate limits.

3.5 Efficient Data Refresh

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Efficient Data Refresh

Strategies to minimize GET API calls:

  • Event-driven retrieval: Trigger updates via notifications (e.g., transaction/order status changes).
  • Targeted retrieval: Fetch data specific to seller needs and marketplaces.
  • Smart scheduling: Align polling with report generation schedules (e.g., FBA reports every 4 hours).
  • Strategic backfills: Use reports for historical data during off-peak hours; implement incremental updates for large datasets.

3.6 Integrated Workflows

Путь: CALLING THE SP-API > Performance Management > Optimize Calls > Integrated Workflows

Combine strategies for optimal efficiency:

  • Order processing: Use Orders API for real-time info, order reports for bulk data, and Notifications API for status updates.
  • Pricing updates: Use PRICING_HEALTH and ANY_OFFER_CHANGED notifications for dynamic pricing.
  • Listings management: Monitor LISTINGS_ITEM_STATUS_CHANGE and LISTINGS_ITEM_ISSUES_CHANGE notifications.
  • MFN fulfillment: Use Notifications API for order status tracking, select shipment services, and process fulfillment.

Key Strategies Summary

  1. Use batch and bulk operations to reduce API call volume.
  2. Implement event-driven architectures with the Notifications API.
  3. Minimize error rates via robust error handling.
  4. Apply efficient data refresh mechanisms.
  5. Create integrated workflows combining multiple optimization techniques.

4. Optimize Rate Limits for Application Workloads

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits for Application Workloads

Manage API throttling and optimize SP-API usage within your application.

When you design your Selling Partner API (SP-API) application, you must consider per-API resource rate limits. SP-API maintains a per-API resource quota for each selling partner to maintain availability and prevent overloading individual APIs. If you exceed these rate limits, SP-API returns a 429 Too Many Requests error and throttles the call. Excessive API throttling can result in job failure, delays, and operational inefficiencies.

This guide outlines the following strategies to help you manage API throttling:

  • Check and adhere to rate limits
  • Avoid spiky traffic
  • Use SP-API pre-built SDKs
  • Implement retry and back-off techniques
  • Reduce the number of API requests

4.1 Check and Adhere to Rate Limits

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits > Check and Adhere to Rate Limits

Review the usage plan for each SP-API operation in the documentation. Compare documented limits with API response rate limit headers (HTTP status codes 20x, 400, 404). For APIs like the Listings API, rate limits depend on both the selling partner account and the calling application. Requests are rate-limited by whichever threshold is reached first.

Steps to monitor and alert errors:

  1. Log API responses (status codes, headers, error messages)
  2. Categorize errors by HTTP status (e.g., 429 rate limit breaches)
  3. Create an error dashboard for visualization
  4. Set alerting thresholds using AWS CloudWatch for proactive notifications.

4.2 Avoid Spiky Traffic

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits > Avoid Spiky Traffic

Distribute API requests uniformly to prevent traffic spikes. Implement a rate limiter to manage traffic volume and maintain a consistent calling pattern based on per-API resource limits.

Example: A rate limiter allows N requests per second aligned with API quotas.

4.3 Use SP-API Pre-Built SDKs

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits > Use SP-API Pre-Built SDKs

Pre-built SDKs (e.g., C#, Java, Python) include built-in rate-limiting capabilities. Implement exception handling for rate limit exceeded errors. For implementation details, refer to SDKs in GitHub.

4.4 Implement Retry and Back-Off Techniques

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits > Implement Retry and Back-Off Techniques

  • Retry: Configure automatic retries with delays based on rate limits.
  • Exponential Back-Off: Use progressively longer waits between retries, capped by maximum delay and retry attempts.
  • Jitter: Add random delays to retries to prevent synchronized bursts of traffic.

4.5 Reduce the Number of API Requests

Путь: CALLING THE SP-API > Performance Management > Optimize Rate Limits > Reduce the Number of API Requests

Optimize code to eliminate unnecessary calls. Use caching for frequently accessed data (e.g., Amazon S3, databases). Stagger SP-API requests in a queue while processing other tasks.
