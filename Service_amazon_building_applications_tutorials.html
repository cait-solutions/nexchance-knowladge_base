1. SP-API SDKs Overview

Build SP-API applications with pre-built and generated SDKs. SP-API offers a collection of software development kits (SDKs) to connect with our APIs. Depending on your preference, you can choose to use a prebuilt or custom SDK:

Prebuilt SDKs

Prebuilt SDKs are maintained by Amazon and can be added to your application with fewer lines of code. SP-API supports prebuilt SDKs for:

  • C#
  • Java
  • JavaScript
  • PHP
  • Python

Custom SDKs

Custom SDKs use a self-service model, where you manually generate an SDK to suit your specific needs. SP-API supports custom SDKs for:

  • C#
  • Java
  • Node.js
  • Python

SP-API SDK tutorials include information about how to automate your SP-API calls with Login with Amazon (LWA) token exchange and authentication.

2. Delete an Application From Your Developer Account

Learn how to delete an app from your developer account. Your existing application can be deleted from your developer account if it meets all of the following conditions:

  • Application is not a sandbox application
  • Application is in draft state and is not published
  • Application is only used on SP-API
  • Application does not have an Amazon Business role
  • Application does not have any existing active OAuth or self-authorizations
Important: If you delete an app or revoke a self-authorization, you cannot undo this action. Refer to the self-authorization workflow to create a new self-authorization.

If your application doesn't meet these conditions, contact the SP-API Developer Support team with the Application ID and the authorization. For sellers, the authorization is the Merchant Customer ID. For vendors, the authorization is the Vendor Group ID.

Delete public and private applications

  1. Sign in to the Solution Provider Portal using your developer credentials.
  2. On the top navigation, select Develop Apps.
  3. For any application, expand the dropdown next to Edit and choose Authorize to navigate to the Manage Authorizations page.
  4. In the Revoke Authorization section, expand Self-Authorizations to view all active self-authorizations.
  5. Choose Revoke for any authorization that you want to remove.
  6. Navigate back to the Solution Provider Portal homepage.
  7. Choose Edit for the application from which you removed self-authorizations in the previous step.
  8. Scroll to the bottom of the page and choose Delete app.
  9. To confirm that you want to proceed, paste the app ID from the confirmation message to the text box.
  10. Choose Delete app.
Warning: You cannot revoke OAuth from your application using this self-service workflow.
Note: To locate Edit app in Seller Central or Vendor Central:
  • Seller Central: Sign in to Seller Central for your marketplace and navigate to Apps and Services, then Develop Apps.
  • Vendor Central: Sign in to Vendor Central for your marketplace and navigate to Integration, then API Integration.

3. Tutorial: Test Selling Partner API Endpoints

Use the sandbox to make test calls without impacting production data. Selling Partner API (SP-API) provides sandbox environments where you can test the SP-API endpoints without affecting production data. You can direct calls to the SP-API sandbox endpoints to make static requests that return mock responses.

Prerequisites

  • A Postman account and workspace.
  • If you have your own selling partner account, you can self authorize your application to access your account information.
  • If you don't have your own selling partner account, you can:
    • Use the Solution Provider Portal to register a sandbox application.
    • Use a third-party OAuth workflow.

Variables Needed to Perform Testing with Postman

  • client_id: You must have the client_id to request an LWA access token. The client_id appears after you register your app.
  • client_secret: You must have the client_secret to request an LWA access token.
  • refresh_token: The LWA refresh token, get this value when the selling partner authorizes your application.
  • base_url_sandbox: To get Selling Partner API sandbox endpoints for each region.

Step-by-Step Workflow

Step 1. Generate a Login with Amazon (LWA) access token

First you need to authorize your application to access selling data on behalf of a selling partner. When you generate a Login with Amazon (LWA) access token, it can be used for multiple SP-API calls until it expires.

The response returns an LWA access token that you can use to authenticate your SP-API call. An LWA access token must be included in calls to all operations (except restricted operations) that return Personally Identifiable Information (PII). When calling restricted operations, you include a Restricted Access Token (RDT) instead of an LWA access token.

Step 2. Make a call to the SP-API sandbox endpoint

  1. Import the Orders API Swagger model to your Postman workspace.
  2. Search the code for an x-amzn-api-sandbox object that contains a static array of request and response examples.
  3. Set the request parameters with the same values that the Orders API Swagger model defines.
  4. Check that your request includes all required parameters as defined in the corresponding Swagger model.
  5. Make a GET Call to /orders/v0/orders.
  6. Set the baseUrl as Selling Partner API sandbox.
  7. Under the Params tab, pass the static request values from the Orders API model.
  8. Under the Headers tab, pass the access_token using the key value pair x-amz-access-token:Atc|********************.
  9. For restricted operations, pass the Restricted Data Token (RDT) using the key value pair x-amz-access-token:Atz.sprdt|********************.
Important: If calling a restricted operation (e.g., accessing PII), use a Restricted Data Token (RDT) instead of an LWA access token. Use the createRestrictedDataToken operation to obtain it.

Example RDT response:

{
  "restrictedDataToken": "Atz.sprdt|IQEBLjAsAhRmHjNgHpi0U-Dme37rR6CuUpSR",
  "expiresIn": 3600
}

Use the Selling Partner API Dynamic Sandbox

The SP-API dynamic sandbox supports stateful, variable responses. Operations supporting dynamic sandbox calls are marked in the Swagger model with:

"x-amzn-api-sandbox": { "dynamic": {} }

4. Tutorial: Automate your SP-API Calls Using a C# SDK

Automate your SP-API calls with Login with Amazon (LWA) token exchange and authentication. This tutorial provides you with all the required information to generate a C# SDK with Login with Amazon (LWA) token exchange and an authentication to build your application.

Prerequisites

  • A hybrid or SP-API app in draft or published state
  • Integrated development environment (IDE) software (e.g., Visual Studio IDE on Windows OS)

Step 1. Set Up Your Workspace

  1. Create a directory named SwaggerToCL.
  2. Download: IDE (e.g., Visual Studio), GNU Wget, Java 8+
  3. Run: 
    wget https://repo1.maven.org/maven2/io/swagger/swagger-codegen-cli/2.4.13/swagger-codegen-cli-2.4.13.jar -O swagger-codegen-cli.jar
  4. Copy swagger-codegen-cli.jar into C:\SwaggerToCL.
  5. Clone models: 
    git clone https://github.com/amzn/selling-partner-api-models
  6. Copy a JSON file (e.g., Sellers.json) into C:\SwaggerToCL.
  7. Download the sellingpartner-api-aa-csharp folder from GitHub.

Step 2. Generate a C# SDK with LWA Token Exchange and Authentication

  1. Open Visual Studio.
  2. Build SellingPartnerAPIAuthAndAuthCSharp.sln to generate Amazon.SellingPartnerAPIAA.dll.
  3. Create csharpConfig.json: 
    {"packageName":"SellingPartnerAPI.SellerAPI","targetFramework":"v4.7.2"}
  4. Generate code: 
    java -jar C:\SwaggerToCL\swagger-codegen-cli.jar generate -i C:\SwaggerToCL\Sellers.json -l csharp -t [path]\templates\ -o C:\SwaggerToCL\Sellers_CsharpCL -c C:\SwaggerToCL\csharpConfig.json

Step 3. Connect to the Selling Partner API Using the Generated C# SDK

  1. Open the generated .sln file in Visual Studio.
  2. Add references:
    • Amazon.SellingPartnerAPIAA.dll
    • NuGet packages: JsonSubTypes 1.2.0+, Newtonsoft.Json 12.0.3+, RestSharp 106.12.0, RateLimiter 2.2.0+
  3. Modify SellersApiTests.cs: 
    LWAAuthorizationCredentials lwaAuthorizationCredentials = new LWAAuthorizationCredentials
{
    ClientId = "amzn1.application-oa2-client.******************",
    ClientSecret = "***********************************",
    RefreshToken = "Atzr|***********************************",
    Endpoint = new Uri("https://api.amazon.com/auth/o2/token")
};
SellersApi sellersApi = new SellersApi.Builder()
    .SetLWAAuthorizationCredentials(lwaAuthorizationCredentials)
    .Build();

GetMarketplaceParticipationsResponse result = sellersApi.GetMarketplaceParticipations();
Console.WriteLine(result.ToJson());

Troubleshooting

  • RestSharp Errors: Update RestSharp to 106.12.0 and verify references.
  • "Newtonsoft could not be found": Manually add Newtonsoft.Json from the packages folder.
  • "ComposableAsync.Core" Error: Add ComposableAsync.Core.dll as a reference.
  • "ToJson() no suitable method found...": Change override to virtual.

5. Tutorial: Automate your SP-API Calls Using a Java SDK

Automate your SP-API calls with Login with Amazon (LWA) token exchange and authentication. This tutorial describes how to generate a Java SDK with LWA token exchange and authentication to build your application seamlessly.

Prerequisites

  • A hybrid or SP-API app in draft or published state
  • An IDE (e.g., Eclipse IDE on Windows OS)

Step 1: Set Up Your Workspace

  1. Create a directory named SwaggerToCL.
  2. Install: Java 17 or newer, Apache Maven 3.9 or greater, GNU Wget 1.20 or greater
  3. Download Swagger Code Generator: 
    wget https://repo1.maven.org/maven2/io/swagger/codegen/v3/swagger-codegen-cli/3.0.61/swagger-codegen-cli-3.0.61.jar
  4. Clone the SP-API models repository: 
    git clone https://github.com/amzn/selling-partner-api-models
  5. Copy JSON files from selling-partner-api-models/models to SwaggerToCL.

Step 2: Generate Java SDK for SP-APIs

Run for each JSON file:

java -jar C:\SwaggerToCL\swagger-codegen-cli.jar generate \
-i [MODEL FILE] \
-l java \
-t [PATH TO TEMPLATES] \
-o [OUTPUT DIRECTORY] \
-c [PATH TO CONFIG.JSON]

Step 3: Build the Authentication/Authorization Library (AA)

  1. Navigate to selling-partner-api-models/clients/sellingpartner-api-aa-java and run: 
    mvn package
  2. Install the JAR in your local Maven repository: 
    mvn install:install-file \
-Dfile=[JAR PATH] \
-DgroupId=com.amazon.sellingpartnerapi \
-DartifactId=sellingpartnerapi-aa-java \
-Dversion=x.x \
-Dpackaging=jar

Step 4: Add the Library as a Dependency

Edit the generated SDK's pom.xml:

<dependency>
  <groupId>com.amazon.sellingpartnerapi</groupId>
  <artifactId>sellingpartnerapi-aa-java</artifactId>
  <version>x.x</version>
</dependency>

Step 5: Connect to the Selling Partner API

Example code using the Sellers API SDK:

import com.amazon.SellingPartnerAPIAA.LWAAuthorizationCredentials;
import io.swagger.client.api.SellersApi;

public class SellersApiDemo {
    public static void main(String[] args) {
        LWAAuthorizationCredentials lwaAuth = LWAAuthorizationCredentials.builder()
            .clientId("amzn1.application-...")
            .clientSecret("...")
            .refreshToken("Atzr|...")
            .endpoint("https://api.amazon.com/auth/o2/token")
            .build();

        SellersApi sellersApi = new SellersApi.Builder()
            .lwaAuthorizationCredentials(lwaAuth)
            .endpoint("https://sellingpartnerapi-na.amazon.com")
            .build();

        try {
            GetMarketplaceParticipationsResponse result = sellersApi.getMarketplaceParticipations();
            System.out.println(result);
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}

For Grantless operations (e.g., Notifications API): Use withScopes(...) to include required OAuth scopes.

npm install ../SellingPartnerAPISdkJavaScriptNode/amzn-testsellingpartnerjavascriptapilwalib-1.0.0.tgz

Step 5: Connect to the Selling Partner API

Create app.config.mjs for credentials (never commit this file):

export const AppConfig = {
    lwaClientId: "<LWA_CLIENT_ID>",
    lwaClientSecret: "<LWA_CLIENT_SECRET>",
    lwaRefreshToken: "<LWA_REFRESH_TOKEN>"
};

Create index.js to execute an API call:

import { AppConfig } from './app.config.mjs';
import { LwaAuthClient } from '@amzn/testsellingpartnerjavascriptapilwalib/src/helper/LwaAuthClient.mjs';
import { SellersApi, ApiClient as SellersApiClient } from '@amzn/testsellingpartnerjavascriptapilwalib/sdk/src/sellers/index.js';

(async () => {
    const lwaClient = new LwaAuthClient(
        AppConfig.lwaClientId,
        AppConfig.lwaClientSecret,
        AppConfig.lwaRefreshToken
    );
    const sellerApiClient = new SellersApiClient('https://sellingpartnerapi-fe.amazon.com');

    const sellerApi = new SellersApi(sellerApiClient);
    sellerApiClient.applyXAmzAccessTokenToRequest(await lwaClient.getAccessToken());

    const participations = await sellerApi.getMarketplaceParticipations();
    console.log(JSON.stringify(participations, null, '  ') + '\n**********************************');
})();

14. Tutorial: Retrieve and Pass a Purchase Order Number to a Carrier

Use the Selling Partner API to retrieve and pass a purchase order (PO) number to UPS, FedEx, or USPS. Business-to-business (B2B/Amazon Business) orders typically include PO numbers on shipping labels. If labels are sourced outside Amazon, the PO number must be retrieved via the Selling Partner API and passed to the carrier.

What is an Amazon Business PO Number?

An Amazon Business PO number is a unique identifier for orders placed by business customers. It is used for:

  • Tracking and reference
  • Billing and accounting
  • Internal management
  • Communication

Tutorial: Retrieve a PO Number Using the Orders API

Prerequisites

  • Authorization from the selling partner
  • The Direct to Consumer Shipping (Restricted) role assigned

Steps

  1. Call the getOrder operation with the orderId path parameter. This is a restricted operation requiring a Restricted Data Token (RDT).
  2. Check the IsBusinessOrder field in the response. If true, the BuyerInfo.PurchaseOrderNumber field will exist.
  3. Retrieve the PO number from the PurchaseOrderNumber field.

Example JSON response:

{
  "payload": {
    "PurchaseOrderNumber": "1234567890123"
  }
}

Tutorial: Retrieve a PO Number Using the Reports API

  1. Call the createReport operation with an order report type.
  2. Poll for REPORT_PROCESSING_FINISHED to get the reportDocumentId.
  3. Call getReportDocument using the reportDocumentId. Requires RDT for restricted report types.
  4. Download the report from the provided URL.
  5. Check the IsBusinessOrder field in the report. If true, the PurchaseOrderNumber field will exist.

Example XML report snippet:

<PurchaseOrderNumber>PO12345</PurchaseOrderNumber>

Tutorial: Pass a PO Number to Carriers

UPS

Use the Shipment operation with ReferenceNumber.Code = "PO":

{
  "ReferenceNumber": [
    {
      "Code": "PO",
      "Value": "CustomerPONum"
    }
  ]
}

FedEx

Use the CreateShipment operation with customerReferenceType = "P_O_NUMBER":

{
  "customerReferences": [
    {
      "customerReferenceType": "P_O_NUMBER",
      "value": "23456764"
    }
  ]
}

USPS

Use the eVS Label API with CustomerRefNo and PrintCustomerRefNo = "true":

<CustomerRefNo>PO: CustomerPONum</CustomerRefNo>
<PrintCustomerRefNo>true</PrintCustomerRefNo>

Auctane (Stamps.com)

Use the CreateIndicium operation with the memo field:

<memo>PO: CustomerPONum</memo>

    "print_custom_1": "CustomerPONum",
